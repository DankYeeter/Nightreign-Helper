# T-002 — Korrektheits- und Regressionsaudit

## Ziel
Ein vollstaendiger, adversarialer Audit des bestehenden Programms auf
Korrektheit. Der Nutzer hat ausdruecklich einen "kompletten Audit" verlangt und
fragt nach offenen Fragen und Problemen, die waehrend der Entwicklung
aufgetreten sind.

## Kontext
- Arbeitskopie: `C:\Users\Daniel\Desktop\ClaudeCode\Nightreign-Helper`,
  Stand 3da8428 (v1.7.1). Der Stand friert waehrend deines Laufs ein.
- **Keine automatisierten Tests im Repo.** Bewerte, was das fuer die
  Releasefaehigkeit bedeutet, und benenne die Stellen, an denen Tests am
  meisten Regressionen verhindert haetten.
- Die Git-Historie ist eine Fundgrube: mehrere Releases waren reine Fixes
  (1.3.1 "measure the loadout group width instead of assuming four Grails",
  1.3.2 "measure every loadout group individually", 1.5.1 equipped mark,
  1.7.1 DLC-Flags). Solche Wiederholungsfehler deuten auf eine Ursache, die
  noch da ist. Sieh dir an, ob die Klasse Fehler wirklich geschlossen ist.
- README "Known limits" nennt selbst mehrere offene Punkte (Attack Rating
  unverifiziert, Save-Scan waehrend des Speicherns liefert falsche Zahlen,
  Break-Threshold unbekannt). Pruefe, ob der Code die dort behaupteten
  Schutzmassnahmen wirklich hat, etwa dass der Reader wartet, bis die Datei
  zur Ruhe gekommen ist.

## Vorgaben
- Priorisiere: kritisch / hoch / mittel / niedrig, jeweils mit Auswirkung fuer
  den Nutzer und der Rolle, an die der Fix geht.
- Suche besonders nach: falschen Zahlen (schlimmer als Abstuerze, weil sie
  glaubwuerdig aussehen), Kopplungen zwischen Tabs, Zustand, der zwischen
  Nightfarern oder Kelchen leckt, Verhalten ohne Savefile, Verhalten ohne
  DLC, Verhalten bei leerem oder beschaedigtem Relikt-Bestand.
- Beantworte ausdruecklich: **pruefen die vorhandenen Mittel ueberhaupt, ob das
  Programm richtig rechnet — oder nur, dass es tut, was es tut?**

## Testumgebung
Windows 10. Das Spiel ist auf diesem Rechner moeglicherweise installiert;
pruefe das, statt es anzunehmen. Ohne Spieldaten sagst du, welche Befunde
deshalb ungeprueft bleiben — du erfindest keine.

## Scope-Grenzen
- NICHT: Anwendungscode aendern. Fixes gehen ueber den `developer`.
- NICHT: den Build-Berater bewerten — den gibt es noch nicht.
- NICHT: Sicherheitsluecken (T-003) oder Designfragen (T-004) — nur wenn sie
  dir auffallen, in einem Satz vermerken.

## Rueckgabeformat
Befundliste im Bericht, jeder Befund mit ID (QA-###), Prioritaet, Ort
(Datei:Zeile), reproduzierbarem Ablauf, erwartetem gegen tatsaechliches
Verhalten. Der Director uebertraegt sie nach `qa/findings.md` — schreibe die
Datei nicht selbst.
